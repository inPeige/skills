# 图文对应规范

口播稿说出来的每句话，画面上必须有东西接着。这份规范定义**怎么把攻略里的图配到口播上**。

---

## 1. 铁律：先看图，再配图

**不许靠文件名、不许靠图片在原文里的位置、不许靠 alt 文本猜内容。**

攻略里的截图往往长得很像（同一个游戏面板的不同页签），
位置相邻也不代表内容对应。必须真的打开看图。

看图的两种方式：
- 模型支持图像输入 → 直接 `read_image`
- 不支持 → 用视觉桥 `modlens_read_image`（本项目已验证可用），
  或者先用 PIL 拼一张带编号的 contact sheet 再一次问完，省 token：
  ```python
  from PIL import Image, ImageDraw
  # 每格左上角标红字编号 01..09，拼成 3x3
  ```
  一次提问要求它逐格转写**画面上的可读文字和数字**——游戏截图的文字
  才是配图价值的来源（NPC 名字、坐标、面板菜单、数值表）。

把每张图的"画面内容"写进 `assets.plan.json` 的 `what` 字段，
后面分镜时不用再回头看图。

### 1.1 contact sheet 有已知失灵场景：**小字数字会读错**

拼图省 token 是对的，但**缩略图里的数字不可信**——2026-09-15 实测：
一张 1266×632 的游戏截图，拼进 3×3 contact sheet 后读数被读成 `410`，
把原图**裁出来放大 3×** 再读是 `470`。两次读数不一致，缩略图那次是错的。

同样这张图，拼图读数还漏了**整块右栏**（黄框内的兑换菜单六宫格），
只看到左栏的 NPC 对话 —— 于是"图里有兑换菜单"这个关键事实被漏判，
下游据此把 s04 的版式设计错了。

**同一次任务里第二次翻车（更严重）**：拼图把两张**同游戏、同面板、不同页签**的截图
读混了——把 A 图的菜单项（`守护兽`/`特殊产出`）记到了 B 图头上。
后果是一整镜的分镜设计建立在一个**图上根本不存在**的目标上
（"四角框套住截图里的『守护兽』菜单项"），而那张图放大 2× 逐字复核后
确认：菜单 11 项里没有这个词。**是缩略图把两张图合成了一个记忆。**

两个失效模式：**①小字数字读错；②近似图互相污染**。第 ② 种更隐蔽——
它读出来的内容是"合理"的，你不会觉得可疑，直到有人去原图上找那个目标。

**规则**：

1. **数字、ID、坐标、金额**——凡是会写进产出物的具体值，
   一律**裁出原图、放大 2–3× 再读一次**，不许用 contact sheet 的读数。
   两次读数不一致时，以放大裁切那次为准，并在产出物里留痕说明曾误读。
2. **拼图读完必须抽查单张**：至少对"这一镜要靠它讲清楚"的那一两张，
   单独再问一次「这张图里有几块区域、分别是什么」——
   缩略图会把边栏、页签、被裁掉的部分一起吃掉。
3. **两次读图结论冲突 = 事实未定**，不要挑一个用；要么再裁再读，
   要么在产出物里标成"待确认"，绝不能当成已核实的事实写进去。
4. **同一站点/同一游戏的多张截图，必须逐张单独问、并在提问里带上"这张是第几张、"
   "和上一张有什么不同"**——拼图里同源截图会互相污染（失效模式 ②）。
   更稳的做法：**先按文件给每张图起一个有辨识度的临时标签**（如"管理员-对话页"/"管理员-告示牌页"），
   提问和记录都带着标签走，不要把两张图放进同一次提问。
5. **凡是要在图上"指一个目标"的卡（放大镜/四角框/聚光/标注/光标），
   目标必须先在原图上被单独确认存在过**——放大了都找不到的目标，
   说明它是从别处串进来的记忆，不是这张图的内容。

```python
# 复核某个具体数字：裁出来放大再读
from PIL import Image
im = Image.open('guide/images/02_xxx.jpg')
W, H = im.size
im.crop((633, 290, W, 390)).resize(((W-633)*3, 300), Image.LANCZOS).save('/tmp/recheck.png')
# 然后对 /tmp/recheck.png 单独调用读图，明确要求"逐字读出数字"
```

## 2. 素材四种类型

| kind | 说明 | 用法 |
|---|---|---|
| `screenshot` | 攻略自带游戏截图，内容直接可用 | 整图或裁局部 |
| `table` | 攻略自带的对照表/数值表截图 | 一般只取局部放大 |
| `ui` | 界面面板截图（菜单、按钮、列表） | 用作"操作演示"画面 |
| `text` | **纯文字/动效镜**，没有图片文件 | 见下 §2.1 |
| `need` | 攻略里**没有**、暂时也不打算补拍的画面 | 进缺口清单 |

### 2.1 `kind: "text"` —— 纯文字镜是一等公民

**不是每段都需要一张图。** 「文字卡 + 动效」是正式做法，不是凑数：
`video-talkcraft` 的 SHOTBOOK 就是写成 `素材：**文**（+ G5 线稿标题框）`。
用户说某几段不补拍时，把那些 `need` 换成 `text` 就对了。

`text` 类素材**没有 `file`**，靠两个字段交付：

```json
{
  "id": "card01",
  "kind": "text",
  "what": "单人 vs 搭伙的积分上限对比卡，把「一天顶两周」做成视觉落差",
  "onScreenText": ["单人 一万五/周", "搭伙 三万/周", "两周 → 一天"],
  "usable": true,
  "usage": "full",
  "segments": ["seg07"]
}
```

- `what` 说这张卡要**干什么**（不是"长什么样"）
- `onScreenText` 是要**打在画面上的字**——talkcraft 的规则是画面文字 ≤12 字提炼、
  不与字幕整句重复，所以这里是关键词不是整句
- 没写 `onScreenText` 会报 W221

什么时候该用文字卡而不是截图：

| 场景 | 选择 |
|---|---|
| 讲一个**对比/反差**（两人份 vs 单人份） | 文字卡更好——数字对比图比截图更有冲击力 |
| 讲一个**流程/机制**（等级→几率→收益） | 线稿示意图（talkcraft 的 G5） |
| 讲一个**具体界面在哪点** | 必须用截图，文字卡替代不了 |
| 开场钩子 | 标题卡是标准做法，不用满世界找空镜 |

`need` 类不是缺陷，是**正常产出**。一篇攻略通常只有 8–12 张图，
而口播稿可能拆出 12–18 段——缺口是必然的，重点是**明确列出来**，
而不是硬拿一张不相干的图凑。

**缺口怎么写**：用一条 `"kind": "need"` 的素材条目表示，
**不给 `file`**，带上 `need`（要拍什么）/ `how`（怎么拿到）/ `priority`。

好处是**只有一个真相源**：每段都能在自己的 `assets` 里引用到东西
（`check_output.py` 的"每段至少一张素材"因此永远可满足），
而"缺口清单"就是 `assets` 里 `kind == "need"` 的那批，
不需要再维护一份 `gaps` 数组去跟它同步。

```bash
# 目前的缺口清单 = assets 里 kind=="need" 的项
python3 -c "import json;d=json.load(open('assets.plan.json'));\
[print(a['priority'], a['id'], a['need']) for a in d['assets'] if a['kind']=='need']"
```

## 3. 覆盖规则

1. **每段至少一张素材**（`check_output.py` E013 强制）
2. **关键信息必须配图**：等级门槛、成本数字、坐标、NPC 位置、操作路径
3. **一个素材可以服务多段**（同一张面板图讲"购买饲料"和"出售动物"），
   但要标注用法差异（换裁剪区域 / 加焦点框）
4. **一段可以配多张**（对比、步骤递进），按出场顺序写进 `assets` 数组
5. **纯口播段允许无图**，但必须在计划里显式写 `usable:false` 或进 `unused`，
   并给出替代方案（文字卡 / 动效 / 生成图）

## 4. 用法标注（`usage`）

| usage | 何时用 | cropHint 该怎么写 |
|---|---|---|
| `full` | 整图信息量够，且比例适合画幅 | 可空 |
| `crop` | 只关心局部（一个对话框、一行数值） | 写清裁哪块，如「取底部对话框区域」 |
| `zoom` | 原图字太小（攻略截图常见 400–700px 宽） | 写清放大倍数与目标区域 |
| `blur-bg` | 只当底图/氛围，不承载信息 | 说明主体放哪 |
| `reference-only` | 不直接上屏，供考据/核对 | 说明依据了什么 |

**游戏截图普遍分辨率低**（实测 392×181 到 1266×632），
竖屏 1080×1920 上直接满屏放会糊。所以 `zoom` 用得很多：
每次只放大一个对话框或一行数值。

## 5. 输出格式

### `assets.plan.json`
```json
{
  "assets": [
    {
      "id": "img01",
      "kind": "screenshot",
      "file": "guide/images/01_19c6bedf.png",
      "source": "https://ok.166.net/reunionpub/1_kol_...",
      "w": 466, "h": 395,
      "what": "大唐境外地图，张猎户 NPC 对话，可领取建造牧场任务",
      "onScreenText": ["大唐境外", "张猎户", "指引"],
      "usable": true,
      "usage": "zoom",
      "cropHint": "放大对话框与 NPC 名字",
      "segments": ["seg02"]
    },
    {
      "id": "need01",
      "kind": "need",
      "what": "牧场全景：动物在栏里走动的画面",
      "need": "牧场全景空镜，用来做开场钩子的底图",
      "how": "游戏内截图 / 录屏一帧：进入自己的牧场，动物成长期",
      "priority": "P0",
      "usable": false,
      "usage": "blur-bg",
      "segments": ["seg01"]
    }
  ],
  "unused": [
    {"id": "img04", "why": "动物种类大全，信息量太大且是查阅型，口播不讲"}
  ]
}
```

`priority`：`P0` = 没它这段讲不清；`P1` = 有更好；`P2` = 锦上添花。

### `file` 的路径规则（踩过坑）

`file` **相对于 `--dir`（产出目录）解析**，而 `fetch_guide.py` 把图写在
`<dir>/guide/images/`。所以值必须写成 **`guide/images/01_xxx.png`**，
写成 `images/01_xxx.png` 会直接吃一个 E011「文件不存在」。

自己做的封面/标题卡放哪都行（比如 `covers/cover.png`），只要路径对得上。

### 哪些素材要和原攻略对账（E015 的作用域）

E015 只检查**声称来自原攻略**的素材，判据二选一：

1. `file` 落在 `guide/images/` 下（默认判据）
2. 显式写了 `"fromGuide": true`

所以下面两种情况都不会被误杀：

- 自己做的封面 / 标题卡 / 示意图 —— 放在 `guide/images/` 之外即可
- **把 `kind:"need"` 补拍项改成真素材**时 —— 新图的路径不在 `guide/images/`
  下（或显式写 `"fromGuide": false`）

反过来，如果你把自建素材放进了 `guide/images/`，就要显式写
`"fromGuide": false`，否则 E015 会以为它是攻略原图。

目标：每张 `guide.json` 里的原图，要么以素材身份出现，要么进 `unused`。
两者都不做会报 W212。

### `kind` / `usage` 是封闭词表（会校验）

`kind` ∈ `screenshot` / `table` / `ui` / `need`
`usage` ∈ `full` / `crop` / `zoom` / `blur-bg` / `reference-only`

写错值报 W219；`file` 不是图片扩展名报 W220。

### `unused` 与 `usable` 的分工

| | 含义 | 谁看 |
|---|---|---|
| `usable: false` | 这张图**不能作为画面用**（补拍占位、水印太重、涉及隐私） | 机器闸据此不再提醒 |
| `unused: [{id, why}]` | 这张图**能用但本期不用**，并写清原因 | 人看，也告诉机器闸"已交代过" |

原攻略里的图只要没进正片，就**要么**在某个段的 `assets` 里，**要么**进 `unused`。
两者都不做，`check_output.py` 会报 W212（原攻略有图没交代）或 W211（可用素材闲置）。

顶层还可以放 `target` / `aspect`（发布平台与画幅），下游分镜会读。

## 6. 与下游分镜（video-talkcraft）的接口

`assets.plan.json` 的每个素材直接对应 SHOTBOOK 每镜的 `素材：` 行：

```
- 素材：图（public/stills/01_19c6bedf.png）
```

- `file` 拷进 `remotion/public/stills/`（保留原名便于追溯）
- `what` 直接抄进分镜的意图行
- `usage` / `cropHint` 决定版式行怎么摆
- `kind: "need"` 且 `priority: "P0"` 的项在分镜前必须补齐，
  否则那一镜只能做成纯文字镜
